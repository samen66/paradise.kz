# design-sync notes for storefront

## Repo shape
- This is a Next.js 16 **application**, not a component-library package — `package.json` has no `main`/`module`/`exports`. There is no `dist/` build. The converter runs in **synth-entry mode** from `srcDir: src/components` (both the `ui/` primitives and the app/feature components).
- Sync scope (user-confirmed): all of `src/components` (~68 files), not just `src/components/ui`. Most feature components (`ProductCard`, `Header`, `CatalogView`, `FilterSidebar`, etc.) depend on `next/navigation`, `next-intl`, `next/image`, or Zustand stores and do not render standalone without the provider wiring below.
- AGENTS.md warns this Next.js version has diverged from training-data Next.js — verified App Router internals against `node_modules/next/dist/docs/` and `node_modules/next/dist/client/components/navigation.js` directly rather than assuming.

## Provider wiring (`cfg.provider`) — superseded in part, see "Module shims" below
- `PreviewProviders` (`.design-sync/support/preview-providers.tsx`, wired via `extraEntries`) wraps every preview in `NextIntlClientProvider` (locale `ru`, messages from `src/messages/ru.json`) — required by every component using `useTranslations`/`useLocale`. It also still sets up mocked `AppRouterContext`/`PathnameContext`/`SearchParamsContext` (defense in depth) and a `globalThis.process = { env: {} }` shim, but **neither actually matters anymore** — see below, the real fix routes around them entirely.

## Module shims (`next/link`, `next/navigation`, `next/image`) — the real fix
- **What broke first**: esbuild-bundling real `next/link` (used directly, and via next-intl's `Link`) pulls in Next's client router internals (`has-base-path.js` → `resolve-href.js` → `is-local-url.js`), which read `process.env.*` at MODULE TOP LEVEL. Webpack shims this via DefinePlugin; esbuild (what this converter uses) doesn't, so `process` is literally undefined in the browser and every preview's bundle init threw `ReferenceError: process is not defined` — **the entire `window.ParadiseStorefront` assignment failed as one unit**, so EVERY component (even ones with zero Next dependency, like `Button`) rendered blank.
- **First attempted fix (didn't work, kept for defense-in-depth)**: adding a `globalThis.process` shim as a top-level side effect in the `extraEntries` module (`preview-providers.tsx`), reasoning that ESM `export * from A; export * from B;` in the generated `.bundle-entry.mjs` evaluates A's whole subgraph before B's. **This assumption was wrong** — verified empirically: the shim code landed in the compiled `_ds_bundle.js` textually AFTER `has-base-path.js`'s crash point, so it never ran in time. esbuild's IIFE linker doesn't preserve "first `export *` branch, fully evaluated, then second" ordering the way native ESM would.
- **Actual fix**: `cfg.tsconfig` points at a **dedicated build-only tsconfig** (`.design-sync/support/tsconfig.design-sync.json`, NOT the app's real `tsconfig.json`) whose `compilerOptions.paths` remaps `next/link` → `.design-sync/support/next-shims/link.tsx`, `next/navigation` → `.../next-shims/navigation.tsx`, `next/image` → `.../next-shims/image.tsx`, alongside the app's own `@/*` alias. The converter's `tsconfigPathsPlugin` (in `lib/bundle.mjs`, not forked) is a generic exact-match esbuild `onResolve` plugin registered with FIRST priority — it intercepts these three specifiers (for every importer, including inside `node_modules/next-intl`, since resolution is global) before they ever reach real Next internals. This is a config-only fix — no fork of `bundle.mjs`/`emit.mjs` (which the base skill explicitly disallows forking) was needed once this lever was found. Bundle size dropped 688KB → 249KB confirming the heavy router-internal chain is gone.
- **Shim contracts** (`.design-sync/support/next-shims/`): `link.tsx` renders a plain `<a href>`; `navigation.tsx` provides `useRouter` (no-op push/replace/refresh/back/forward/prefetch — this is the one hook that hard-crashes on a null `AppRouterContext`, confirmed by reading `navigation.js` directly), `usePathname` (`"/"`), `useSearchParams` (empty `URLSearchParams`), `useParams` (`{}`); `image.tsx` renders a plain `<img src>` (maps `fill` to absolute-position CSS, drops `sizes`/`priority`/`quality`/`loader`). **Known limitation**: `next/image` previews show real `<img>` tags but any relative/API-backed `src` won't resolve to a real image without a reachable backend — same caveat as the data-fetching section below.
- Verified via Chrome (not the Playwright render-check, which the user opted to skip): `.review.html` after these fixes shows real rendered content — `LocaleSwitcher` renders actual "Рус"/"Қаз" text pulled through the mocked `NextIntlClientProvider`, `SortSelect` renders a real styled `<select>` with translated options, `Input`/`Badge`/`Button` show real Tailwind styling. Remaining console errors are all ordinary "required prop is `undefined`" crashes from unauthored floor-card default props (e.g. `ProductCard` reading `product.slug`) — expected and resolved by preview authoring (§4), not a build problem.

## Styling
- `globals.css` is Tailwind v4 CSS-first config (`@theme` + `@import "tailwindcss"`) — it has NO generated utility classes on its own; it must go through the project's real PostCSS/Tailwind compiler or previews render unstyled.
- `cfg.cssEntry` points at `.ds-sync/generated-globals.css`, produced by running the app's own `@tailwindcss/postcss` plugin over `src/app/globals.css` via a small Node script (see the compile step — `postcss([tailwindcssPostcss({ base: repoRoot })]).process(...)`). **`.ds-sync/` is gitignored**, so a re-sync must re-run this compile step before `package-build.mjs` — it does not persist across clones. Command (from repo root):
  ```
  node -e '
  const postcss = require("postcss");
  const tw = require("@tailwindcss/postcss");
  const fs = require("fs");
  const css = fs.readFileSync("src/app/globals.css", "utf8");
  postcss([tw({ base: process.cwd() })])
    .process(css, { from: "src/app/globals.css", to: ".ds-sync/generated-globals.css" })
    .then(r => { fs.mkdirSync(".ds-sync", { recursive: true }); fs.writeFileSync(".ds-sync/generated-globals.css", r.css); });
  '
  ```

## Fonts
- `Golos Text` (weight 400 — the app never requests other weights via `next/font`) and `Manrope` (weights 500/600/700/800) are real Google Fonts self-hosted by `next/font/google` in the app; `next/font`'s build-time cache (`.next/dev/static/media/*.woff2`) has no readable family/weight mapping, so instead of reverse-engineering that cache, real webfont files were downloaded fresh from `fonts.googleapis.com`/`fonts.gstatic.com` (the same source `next/font` itself pulls from) into `.design-sync/support/fonts/`, with `@font-face` + a `:root { --font-golos; --font-display-src }` mapping in `.design-sync/support/fonts.css` (wired via `cfg.extraFonts`) — these are committed, durable, and don't need re-fetching on re-sync.
- **Known limitation**: Golos Text's `wght@500`/`600` css2 responses resolved to the *same* file as `400` (Golos Text apparently only ships a 400 static instance) — so any Golos Text 500/600 usage in the app renders visually as regular weight in previews. Manrope's 500–800 files are genuinely distinct.

## Excluded: true async Server Components
- `Header.tsx`, `Footer.tsx`, `CatalogView.tsx`, `Breadcrumbs.tsx` are `export async function` React Server Components using `next-intl/server`'s `getTranslations()` (server-only, request-scoped — not just "needs a provider"). Confirmed via browser console: React itself throws `<Name> is an async Client Component. Only Server Components can be async at the moment` when esbuild bundles one into a client IIFE and ReactDOM tries to mount it — this is not fixable by mocking props/context, it's structural (RSCs require the RSC server runtime, full stop). Excluded via `cfg.componentSrcMap: {Header: null, Footer: null, CatalogView: null, Breadcrumbs: null}`.
- Their `b2b/` counterparts (`B2BHeader`, `B2BFooter`, `B2BCatalogView`) are ordinary `"use client"` components (client-side fetch instead of server-side), so they ARE included and render normally — this asymmetry is real, not an oversight.
- If these should appear in Claude Design, the app would need a pure presentational split (e.g. `Header` (RSC, fetches) → renders `HeaderView` (client, props-only)) so the client-safe half can sync — that's a source-code decision for the app team, out of scope for this sync (see "ship what's already built" in the base skill).

## Data-fetching components
- `Footer.tsx`, `CatalogView.tsx`, `FavoriteButton.tsx`, `src/components/b2b/B2BCatalogView.tsx` call `apiGet`/`fetch` directly rather than receiving data via props. Real network calls will fail in the preview sandbox (no reachable backend) — resolve per-component during preview authoring (compose around the fetch, or accept the caught-error fallback UI as the preview state) rather than assuming these are broken.

## 2026-07-21 preview-authoring sweep: all 17 remaining floor cards authored

Picked up the standing offer from the last re-sync entry — authored previews for every one of the 17 components that were still floor cards (AccountLink, ActiveFilters, AddToCartButton, BannerCarousel, Carousel, CartBadge, CategoryIcons, FavoriteButton, FilterSidebar, LocaleSwitcher, ProductGallery, SearchBox, SortSelect, AddToCartB2BButton, B2BCatalogView, B2BHeader, B2BFooter). All 31 components now have authored previews graded `good`, none left on the floor. Worked solo on 5 (the ones needing a new technique) then fanned out 3 subagents over the remaining 12 in disjoint batches (each restricted to its own preview files + grade jsons + a learnings file; only `preview-rebuild.mjs --components <theirs>` + scoped `package-capture.mjs`, never the full build).

- **Real Zustand stores, not mocked — seed them directly.** `useAuth` (`@/lib/auth`), `useCart` (`@/lib/cart`), `useB2bCart` (`@/stores/useB2bCart`), `useB2bAuth` (`@/stores/useB2bAuth`) are genuine persisted stores with no provider-level mock. Every preview needing a specific auth/cart state calls `store.setState({...FULL state...})` synchronously in the story's function body (not a `useEffect` — avoids an extra render and works because the child reads the store during its own first render, which happens after the parent's synchronous call completes). Always set the *full* state, never just changed fields — `persist` middleware rehydrates from localStorage at module load and can carry over a previous capture's state otherwise. See `.design-sync/previews/{AccountLink,CartBadge,AddToCartB2BButton,FavoriteButton,B2BCatalogView,B2BHeader}.tsx` for the working idiom.
- **Known limitation, confirmed root cause, don't fix: an off-by-one capture-lag artifact hits multi-story Zustand-seeded preview files.** `package-capture.mjs` captures each story via its own real `page.goto(...?story=<Name>)` navigation (genuinely isolated — only that one export mounts, confirmed by reading `lib/emit.mjs`'s generated script), so this is NOT the "simultaneous grid mount sharing state" bug it first looks like. The actual mechanism, confirmed by direct experiment (see the `B2BHeader` investigation below): **each story's screenshot displays the *previous* navigation's true final paint, not its own** — a Chromium/Playwright compositor timing quirk where `waitUntil: 'networkidle'` resolves for a same-origin static-file load (no real network latency) before the new page's frame has actually replaced the old one. Proven by: (1) two-story `B2BHeader.tsx` consistently shows `Guest` with the profile icon (wrong) and `SignedIn` without it (wrong) — an exact swap; (2) reversing the file's export declaration order changed nothing (rules out source/declaration-order dependence); (3) reducing the file to **just one** story at a time made that story render *correctly* every time (rules out a Zustand/localStorage/rehydration bug in the component or the seeding pattern itself — zustand's `persist` middleware rehydration is fully synchronous for the default localStorage backend, confirmed by reading `node_modules/zustand/esm/middleware.mjs`, so there's no async race there either). The 1-story case can never expose this artifact even if present, since "previous" and "current" intended values are identical there — that's exactly why it looked "fine" for some components (a false negative, not proof of absence).
  - **Affected so far**: `CartBadge` (batch1's "Empty"/"WithItems" — likely this same mechanism, not a Zustand bug as originally guessed) and `B2BHeader` (`Guest`/`SignedIn`) — both graded `good` since each story was verified correct in isolation.
  - **Verification technique for a suspicious multi-story capture**: temporarily reduce the preview file to one story, `preview-rebuild.mjs --components <Name>` + `package-capture.mjs --components <Name>`, confirm it renders correctly alone, repeat for the other stor(y/ies), then restore the full file. This isolates "is the component/seed logic correct" from "is this capture-pipeline artifact painting the wrong frame."
  - **Not a fix candidate**: this lives in the shared `package-capture.mjs`/Playwright-Chromium interaction, not in `config.json` or any authored `.tsx` — no per-repo override exists for it. The real uploaded `_ds_bundle.js` is completely unaffected (a design agent composing with the real `B2BHeader`/`CartBadge` gets correct live behavior); only the static preview-card screenshot used for grading/review can show a stale frame for this specific pattern (2+ stories that each synchronously seed a shared external store to a *different* value).
- **"Compose around the fetch" works great for real components, not just error states — use it when the payoff is a real success-path render.** `FavoriteButton` and `B2BCatalogView` both fetch their own data on mount with no data props. Rather than settling for the documented-acceptable "caught-error fallback" state, both got a thin `window.fetch` stub (real `fetch.bind(window)` saved first, then overridden to answer only the specific URL substrings the component calls with realistic JSON `Response` objects, falling through to the real fetch for anything else). This drives the *real* component through its *real* success path — for `B2BCatalogView` this means the actual filter sidebar + product grid + pagination render with sample data instead of a bare "failed to load" message, which is a dramatically more useful card for a design agent to compose with. Not a reimplementation: the real component code runs untouched, only the network layer is faked, same spirit as any Storybook/MSW mock.
- **`hidden lg:inline` / `lg:hidden` gated content needs a wide viewport override — audit source classNames for this pattern proactively.** Beyond the already-known `HeaderBurger` case, this sweep found the same root cause in `AccountLink`, `CartBadge`, and `B2BHeader` (all header-row icon+label links whose label is `hidden lg:inline`) and in `FilterSidebar` (whose entire desktop `<aside>` is `hidden lg:block`, with the mobile trigger button as the `lg:hidden` counterpart). Fixed via `cfg.overrides.<Name>: {"viewport": "<W>x<H>"}` with W ≥ 1024 (see `config.json`: `AccountLink`/`CartBadge` at `1100x120`, `B2BHeader` at `1200x160`, `FilterSidebar` at `1100x1080` with `cardMode: "single"` since it's a big composition). A plain `md:grid-cols-N` reflow (e.g. `B2BFooter`'s 4→2 column reflow at 900px) is NOT the same problem — nothing is hidden, just reflowed — and does not need an override.
- **`cfg.overrides.<Name>.viewport` is global to the component, not per-story.** This means a component with two responsive-gated layouts that need *opposite* viewport widths (e.g. `FilterSidebar`'s desktop aside vs. its mobile drawer-open state) can only ever show one of them well in this harness. Picked the more valuable one (desktop) and swept the achievable prop axis instead (`isB2B`) rather than fighting the harness. Documented as a hard ceiling, not a bug to chase.
- **`useSearchParams()` (via the `next/navigation` shim) always returns an empty `URLSearchParams`.** Any component deriving its visible state entirely from URL search params (not from real props) has no way to show a "with active filters/sort" story except through whatever real props it does accept. `FilterSidebar` (`isB2B`), `SortSelect` (`isB2B`), `ActiveFilters` (`searchParams`/`pathname` are genuine props here, not from the hook) were all handled per their actual API; `SearchBox` and `LocaleSwitcher` have no such prop and are capped at one deterministic story each (`LocaleSwitcher` additionally can't show `kk`-active since the preview's `NextIntlClientProvider` locale is fixed at `"ru"` globally, not story-overridable).
- **Ref + real DOM event dispatch is the pattern for uncontrolled post-interaction state**, extending the existing `MegaMenu` precedent (`dispatchEvent(new MouseEvent("mouseover", ...))`) to plain clicks: `AddToCartButton`'s `JustAdded` confirmation state and `ProductGallery`'s `ActiveThumbnail` bordered-highlight both use a ref + `useEffect` that calls the real DOM node's `.click()` shortly after mount, driving the component through its actual internal state transition rather than faking the visual.
- **`CategoryIcons`' real slugs don't match its own icon map — composed matching data instead of reusing `sampleCategories` verbatim.** The component keys its emoji off `category.slug` (`sofa`/`bed`/`chair`/`storage`/`table`/`default`), but the repo's real category slugs are Russian transliterations (`divany`, `kresla`, ...) that all fall through to the default house icon. Authored a small local fixture (inline in the preview file, not `sample-data.ts`) with slugs that actually hit each icon — legitimate composition (real prop shape, deliberately chosen values), not reimplementation.
- **Native `<select>` prop-driven DOM differences can be invisible in a closed-dropdown screenshot.** `SortSelect`'s `isB2B` correctly removes two `<option>`s from the DOM, but a closed `<select>` only ever paints its selected option's label, so `Retail`/`B2B` stories are pixel-identical despite differing markup — not a bug, just a ceiling of static screenshot grading for native form controls.
- **Some prop axes are real but don't cause any visual difference** — `AddToCartButton`'s `isB2B` only changes which cart store `handleAdd()` targets, not anything rendered, so its `Compact`/`CompactB2B` stories are intentionally pixel-identical. Kept both anyway since they're each a distinct real usage, just noting it so a future sync doesn't mistake it for a rendering bug.
- **Widen wrapper divs generously for horizontally-scrolling components.** `CategoryIcons`' own `overflow-x-auto` + edge-fade mask is real, intentional scroll affordance, but an under-sized story wrapper (first attempt: `max-w-2xl`) clipped the last icon at the container edge, which reads as a "Complete" rubric failure even though the component itself is working correctly. Sized generously (`max-w-4xl`) to fit all icons without relying on the scroll.
- **`Carousel` (the generic horizontal-scroll wrapper, not a product-specific component) was composed exactly like its one real call site** in `src/app/[locale]/page.tsx` (wrapping `ProductCard` in the app's own real responsive-width wrapper div) rather than inventing a generic composition — matches "the story set the DS team would have written."
- **CONFIG_STALE gotcha for orchestrator/subagent handoffs**: adding a new `cfg.overrides` entry to `config.json` *after* the last full `package-build.mjs` run leaves `ds-bundle/.stories-map.json`'s stamped config hash stale for that component. `preview-rebuild.mjs` correctly refuses with `[CONFIG_STALE]` rather than building against it. Any override added mid-session (as `B2BHeader`'s was, added after the FavoriteButton/B2BCatalogView solo build) needs one full `package-build.mjs` re-stamp before a scoped subagent rebuild for that component will succeed — plan config overrides *before* kicking off parallel subagent waves when possible, or expect exactly one component to need a follow-up full rebuild.

## Re-sync risks
- The Tailwind CSS compile step and the font files are NOT anchored to app changes — if `globals.css` tokens change, or the app starts using a Golos Text/Manrope weight not fetched here, this must be caught manually (no automatic drift detection). Re-run the compile step above on every re-sync regardless, since it's cheap and deterministic.
- `PreviewProviders` reaches into Next's internal (undocumented but stable across the 13–16 App Router line) `next/dist/shared/lib/*.shared-runtime` modules. A future Next major could rename/remove these — if `package-build.mjs` reports `[UNRESOLVED_IMPORT]` for either shared-runtime path, that's the first place to look.
- Sync scope was a deliberate call to include the full `src/components` tree despite most of it being app-coupled, not a pure design system — expect a meaningfully higher floor-card ratio than a typical DS repo.
- Playwright/Chromium is still not installed locally — every build in this repo has run with `--no-render-check`. Grading has so far relied on reading capture screenshots directly (which does catch real rendering bugs, as the `HeaderBurger`/`ToastContainer` fixes above show), but the automated `bad`/`thin`/`variantsIdentical` gate in `package-validate.mjs` has never actually run. If a future sync wants that gate, install playwright + chromium first (base skill §4.1).
- Always end a sync by writing `_ds_sync.json` and committing `.design-sync/` — this session's biggest time cost was recovering from a prior run that skipped both. Before starting new preview authoring work, check `git status` for `.design-sync/` — if it shows as entirely untracked, the previous session's work was never committed.
