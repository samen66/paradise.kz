# Перенос back-office из Filament в `admin/` — этап 2: склад

Дата: 2026-09-17
Статус: дизайн согласован, ждёт ревью спека
Предыдущий этап: `docs/superpowers/specs/2026-09-17-admin-catalog-migration-design.md`

## Цель

Складской учёт ведётся в `admin/`, без Filament: склады, поставщики, приёмки,
новый документ «Списание» и история движений. Filament-ресурсы склада работают
параллельно до этапа 5 (удаление Filament).

## Принятые решения

- **Объём:** перенос складов, поставщиков и приёмок (с чисткой) + документ
  «Списание» + просмотр движений. Инвентаризация, перемещения, печать и отчёты —
  не в этом этапе.
- **Списание — документ, как приёмка** (черновик → «Провести», необратимо),
  отдельные таблицы `write_offs` / `write_off_items` и `WriteOffService`.
  Отвергнуты: общая таблица `stock_documents` (миграция приёмок и их
  `documentable`-ссылок, переписывание проверенного сервиса ради двух
  документов) и списание без документа (нет черновика и пакетных списаний).
- **Движения — только чтение.**
- API и экраны строятся по образцу этапа 1: REST-контроллер на ресурс +
  `FormRequest`, общие компоненты `admin/src/components/ui`, `useResource`.

## Что найдено в текущем коде

- `stores` связаны с `batches`, `stock_movements`, `product_store_stock`,
  `goods_receipts` через `cascadeOnDelete`, а Filament разрешает удалять склады
  (в том числе массово) и проведённые приёмки — удаление стирает историю учёта.
- `GoodsReceiptService::post` проверяет `isPosted()` без блокировки: два
  параллельных «Провести» проводят приёмку дважды.
- В `StockMovement` есть типы `write_off`, `adjustment`, `stocktake`,
  `transfer_in/out`, но `FifoInventoryService` умеет только `receive` и `issue`;
  `issue(type:, document:)` уже подходит для списания.
- `stores.is_default` и порядок `is_default desc, name` использует
  `StoreResolver` и публичный список складов — поля `code`, `type`, `address`,
  `is_default` в Filament-форме не показаны, но влияют на витрину.

## 1. Данные и API (`/api/admin/*`, `auth:sanctum` + `role:admin|manager`)

### Новые таблицы

`write_offs`: `id`, `store_id` (FK, restrict on delete), `reason`
(`damaged` | `lost` | `regrading` | `other`), `note` (text, nullable),
`status` (`draft` | `posted`, default `draft`), `posted_at` (nullable),
`user_id` (nullable, nullOnDelete), timestamps.

`write_off_items`: `id`, `write_off_id` (FK, cascadeOnDelete), `product_id`
(FK, restrict on delete), `quantity` (decimal 12,3), timestamps.

Себестоимость в документе не хранится — она в движениях `write_off`.
Подпись документа — «Списание №<id>».

### Эндпоинты

| Ресурс | Эндпоинты | Правила |
|---|---|---|
| Склады (`Store`) | `apiResource stores` | `name` (обяз.), `code`, `type` (`warehouse`\|`retail_point`), `address`, `is_active`, `is_default`. `is_default` — ровно у одного: установка в одной транзакции снимает флаг с остальных. `source`/`external_id` не принимаются и не отдаются. Удаление склада, у которого есть движения, партии, приёмки, списания или заказы → 422. Выключение или удаление последнего активного склада → 422 |
| Поставщики (`Supplier`) | `apiResource suppliers` (index: `filter[search]` по названию и БИН) | `name` (обяз.), `bin`, `phone`, `email`, `note`, `is_active`. Удаление поставщика с приёмками → 422 |
| Приёмки (`GoodsReceipt`) | `apiResource goods-receipts` (index: фильтры `status`, `store_id`; пагинация) + `POST goods-receipts/{goods_receipt}/post` | Шапка: `supplier_id`, `store_id` (обяз.), `number`, `received_at`, `note`. Index/show отдают `items_count`, `total_cost` (тиын), `store`, `supplier`, `user` (id, name). Изменение/удаление проведённой → 422 «Документ проведён». `post` → `GoodsReceiptService::post`; `RuntimeException` → 422 с текстом |
| Позиции приёмки | `goods-receipts/{goods_receipt}/items` — index/store/update/destroy (scoped) | `product_id`, `quantity` (> 0, до 3 знаков), `unit_cost` (₸ → тиын через `ConvertsTengeToTiyn`). Для проведённой — 422 |
| Списания (`WriteOff`) | `apiResource write-offs` (фильтры `status`, `store_id`, `reason`; пагинация) + `POST write-offs/{write_off}/post` | Шапка: `store_id` (обяз.), `reason` (обяз.), `note`. Изменение/удаление проведённого → 422. `post` → `WriteOffService::post` |
| Позиции списания | `write-offs/{write_off}/items` — index/store/update/destroy (scoped) | `product_id`, `quantity` (> 0, до 3 знаков). Index отдаёт у позиции `available` — текущий остаток товара на складе документа. Для проведённого — 422 |
| Движения (`StockMovement`) | `GET stock-movements` | Только чтение. Фильтры: `product_id`, `store_id`, `type`, `from`, `to` (даты). Сортировка `-created_at`, пагинация 50. Строка: `id`, `created_at`, `store {id, name}`, `product {id, name, code}`, `type`, `qty_delta`, `unit_cost`, `balance_after`, `document {type: receipt\|write_off\|order, id, label} \| null`, `user {id, name} \| null`, `note` |

### Сервисы

- `WriteOffService::post(WriteOff, ?User)`: в транзакции перечитывает документ
  с `lockForUpdate()`, проверяет статус (проведён → `RuntimeException`), пустой
  документ → `RuntimeException`; для каждой позиции
  `FifoInventoryService::issue(type: write_off, document: $writeOff, user:)`;
  `InsufficientStockException` откатывает всё и превращается в 422
  «Не хватает: <товар> — нужно N, доступно M»; затем `status=posted`,
  `posted_at`, `user_id`.
- `GoodsReceiptService::post` получает ту же блокировку и повторную проверку
  статуса внутри транзакции.

### Общие правила (как на этапе 1)

`{data}` для записи, `{data: [...]}` для связей, пагинатор для журналов
(приёмки, списания, движения), 204 на удаление, 422 `{message}` на запреты,
404 на чужую позицию (scoped). Частичное обновление не сбрасывает пропущенные
поля. `declare(strict_types=1);`.

## 2. Экраны `admin/`

Меню, группа «Запасы»: «Склад» (остатки, существующий), «Движения», «Приёмки»,
«Списания», «Склады», «Поставщики».

- **`/stores`** — таблица + `CrudModal`: название, код, тип, адрес, «Доступен
  клиентам», «По умолчанию» (отметка в строке). Отказ в удалении/выключении —
  сообщение сервера.
- **`/suppliers`** — таблица с поиском + `CrudModal`.
- **`/goods-receipts`** — номер, дата, поставщик, склад, позиций, сумма,
  статус; фильтры статус/склад; «Новая приёмка» → модалка шапки → карточка.
- **`/goods-receipts/[id]`** — черновик: шапка правится, позиции через
  `EntityPicker` (товар) с количеством и себестоимостью в ₸, итог; «Провести»
  (подтверждение «Будут созданы партии и движения по складу. Необратимо.») и
  «Удалить черновик». Проведённая — только чтение, «Проведена <дата>, <кто>»,
  ссылка «Движения по этой приёмке».
- **`/write-offs`** и **`/write-offs/[id]`** — то же для списаний: склад,
  причина, комментарий, позиции «товар + количество» с колонкой «Доступно»;
  ошибка нехватки из 422; проведённое показывает себестоимость по движениям.
- **`/stock-movements`** — фильтры склад, тип, период, товар (`EntityPicker`),
  отражаются в URL; колонки: дата, склад, товар, тип (приход / продажа /
  возврат / списание), ±кол-во (зелёный/красный), себестоимость, остаток после,
  документ (ссылка на приёмку, списание или `/orders/[id]`), пользователь.
- **`/stock`** — в строке ссылка «Движения» →
  `/stock-movements?product_id=&store_id=`; «Приёмки» ведёт на
  `/goods-receipts`.
- **`NoActiveStoreWarning`** — «Настроить склады» ведёт на `/stores` (текст
  ссылки не меняется: на него опирается `admin/e2e/stock.spec.ts`).

Кнопка «Провести» блокируется на время запроса и после ответа перечитывает
документ. `ERP_ADMIN_URL` остаётся для экранов этапов 3–4.

## 3. Права, ошибки, конкурентность

- Доступ — `admin` и `manager`, без отдельного права на проведение.
- Двойное проведение исключено блокировкой строки документа в сервисах.
- Нехватка при списании откатывает всю транзакцию.
- Ошибки на клиенте — механизм этапа 1 (интерсептор, 422 в форму или toast).
- Filament-ресурсы склада работают до этапа 5 на тех же данных; списания есть
  только в `admin/`.

## 4. Тестирование

- **PHPUnit** — по тесту на контроллер: доступ, валидация, запреты 422
  (удаление склада с историей, последний активный склад, поставщик с
  приёмками, правка проведённых документов), scoped 404, ₸ → тиын,
  единственность `is_default`, фильтры движений и формат `document`.
- **`WriteOffServiceTest`** — FIFO-себестоимость по нескольким партиям,
  нехватка откатывает все позиции, повторное проведение и пустой документ
  запрещены.
- **`GoodsReceiptServiceTest`** — повторное проведение не меняет остаток.
- **admin/** — `npx tsc --noEmit && npm run build`.
- **Playwright** (`admin/e2e`, уборка через API как на этапе 1): поставщик →
  черновик приёмки → позиция → «Провести» → остаток в `/stock` вырос → движение
  в `/stock-movements`; списание больше остатка → «Не хватает» → исправить →
  проведено; удалить склад с историей нельзя. Товар и склад тест создаёт сам,
  склад — **неактивным** (иначе `StoreResolver` может сделать его основным для
  витрины); общие фикстуры (`in_stock_product` и др.) не трогаются. Проведённые
  документы не удаляются — тестовые данные помечаются префиксом `E2E`.

## 5. Выкатка

- Ветка `feat/admin-warehouse`, один PR.
- Миграция `create_write_offs_tables` — только новые таблицы; применяется
  штатным `migrate --force` в `deploy.yml`.
- Существующие контракты (`GET /admin/stock`, публичный список складов) не
  меняются.

## Критерий готовности

Менеджер ведёт склады и поставщиков, оформляет и проводит приёмки и списания и
смотрит движения в `admin/`, не заходя в Filament; PHPUnit, `tsc`/`build` и
e2e этапа 2 зелёные.

## Вне этапа 2

Инвентаризация (`stocktake`/`adjustment`), перемещения между складами, печать
документов, отчёты по себестоимости и оборотам, разделение прав на проведение.
