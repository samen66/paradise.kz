# Экран заказов в админке: сегменты B2B/розница, вкладки по статусам, действия из списка

## Контекст

`admin/src/app/orders/page.tsx` — 232 строки в одном файле: поиск, выпадающий
список из семи статусов, таблица, пагинация по 20. Всё состояние живёт в
`useState`, поэтому ссылку на отфильтрованный список нельзя передать, а F5
сбрасывает фильтры. Сегмент клиента (B2B или розница) на экране не виден вообще.

`App\Http\Controllers\Api\Admin\OrderController::index` отдаёт
`QueryBuilder::for(Order::class)` с фильтрами `status`, `type`, `search`,
`->with(['user'])`, `->latest()->paginate(20)`. Счётчиков по статусам в ответе нет.

Два куска кода мертвы:

- `AllowedFilter::exact('type')` в контроллере — колонки `type` в таблице `orders`
  нет (`database/migrations/2026_06_26_000009_create_orders_table.php` и все
  последующие миграции по `orders` её не добавляют).
- Колонка «Тип: Бронь / Заказ» в таблице списка читает `order.type` и поэтому
  всегда рисует «Заказ».

Сегмент клиента хранится на пользователе: `users.type` со значениями
`b2b` и `retail` (`User::TYPE_B2B`, `User::TYPE_RETAIL`), плюс флаг
`users.is_guest` для гостевого оформления. Filament уже показывает сегмент
заказа именно через связь с пользователем
(`app/Filament/Resources/Orders/Tables/OrdersTable.php:62`).

Смена статуса доступна только внутри карточки заказа
(`admin/src/app/orders/[id]/page.tsx:272`): выпадашка плюс кнопка «Сохранить».
Валидация на API — `in:Order::CLIENT_STATUSES`, то есть любой заказ можно
перевести в любой рабочий статус, включая откат завершённого в «новый».

## Цели

1. Менеджер разделяет заказы по сегменту: «Все», «B2B», «Розница».
2. Внутри сегмента заказы разложены по вкладкам статусов со счётчиками:
   «Все», «Новые», «Подтверждённые», «В доставке», «Завершённые», «Отменённые»,
   «Архив».
3. Статус меняется прямо из строки списка, без захода в карточку.
4. Состояние экрана (сегмент, статус, поиск, страница) живёт в URL.
5. Страница разложена на компоненты; лейблы и цвета статусов перестают
   дублироваться между списком и карточкой заказа.

## Не цели

- **Массовые действия** (чекбоксы, «подтвердить выбранные»). Добавляются поверх
  этого дизайна отдельно, если ежедневный объём заказов этого потребует.
- **Колонка `orders.channel`** со снапшотом сегмента на момент оформления.
  Обоснование — в разделе «Сегмент берём с пользователя».
- Сохранённые фильтры, экспорт, реалтайм-обновление списка.
- Возврат «броней» (`type = reservation`): сущности в БД нет, восстанавливать
  её в этой задаче не будем — мёртвый код просто удаляем.
- Правки Filament-ресурса заказов. Он остаётся как есть.
- Зоны админки (B2B / Клиенты / CRM), разделение бэкенда на сервисы. Это
  отдельные циклы проектирования.

## Решения

### Сегмент берём с пользователя, без новой колонки

`filter[segment]` со значениями `b2b` и `retail` — `AllowedFilter::callback`,
который ограничивает выборку через `whereHas('user', ...)` по `users.type`.
Гостевые заказы (`users.is_guest = true`, тип `retail`) попадают в розницу.

Альтернатива — завести на заказе колонку `channel` и писать в неё снапшот
сегмента при оформлении, по аналогии со снапшотом цен. Отвергнута: тип
пользователя не переключается между `b2b` и `retail` ни на одном пути записи, и
это защищено намеренно — розничный OTP-логин отказывается обслуживать
b2b-аккаунт (`app/Services/Auth/OtpService.php:175`), а
`B2bPhoneAuthService` отказывается работать с не-b2b аккаунтом
(`app/Services/Auth/B2bPhoneAuthService.php:102`). Единственный апгрейд —
гость становится полноценным `retail` (`OtpService.php:182`), и сегмент при этом
не меняется. Значит «переезда» исторических заказов между сегментами не бывает,
а миграция с бэкфиллом и правкой трёх путей оформления дала бы ноль выигрыша.

Если когда-нибудь появится смена типа клиента — колонку нужно будет завести, и
этот абзац объясняет, почему тогда, а не сейчас.

**Заодно удаляется мёртвый код:** `AllowedFilter::exact('type')` из контроллера
и колонка «Тип» из таблицы списка.

### Счётчики едут в `meta.status_counts`

`index` возвращает пагинатор; к нему добавляется ключ `meta.status_counts`:

```json
{
  "all": 42, "pending": 3, "confirmed": 7, "in_delivery": 2,
  "completed": 28, "cancelled": 1, "archived": 1
}
```

`archived` — сумма легаси-статусов `synced` и `failed`.

Вкладка «Архив» шлёт `filter[status]=archived`, и это **псевдостатус**: такого
значения в колонке `orders.status` не бывает. Поэтому `AllowedFilter::exact('status')`
заменяется на `AllowedFilter::callback`, который разворачивает `archived` в
`whereIn('status', ['synced', 'failed'])`, а любое другое значение сравнивает
точно. Вкладка «Все» параметр `status` не шлёт вовсе.

**Правило согласованности:** счётчики считаются по тому же базовому запросу, но
**с применённым сегментом и поиском и без применённого фильтра статуса**. Иначе
на активной вкладке стоял бы её размер, а на всех остальных — нули.

Реализация: базовый запрос собирается один раз, из него делается клон под
`GROUP BY status` для счётчиков и основной — под пагинацию. Отдельного эндпоинта
`/counts` не заводим: одна поездка на экран, счётчики не могут разъехаться со
списком.

### Состояние экрана — в URL

`/orders?segment=b2b&status=pending&q=диван&page=2`.

Вкладки — это `<Link>`, а не обработчики `onClick` над `useState`. Следствия:
ссылку на «новые B2B» можно отправить коллеге, F5 не сбрасывает фильтры, кнопка
«назад» в браузере работает. Поиск остаётся полем ввода с debounce 300 мс, но
по срабатыванию переписывает `q` в URL (`router.replace`, без новой записи в
истории — иначе «назад» отматывало бы по букве).

Умолчания при отсутствии параметров: `segment=all`, `status=all`, `page=1`.
Неизвестное значение параметра трактуется как умолчание, а не как ошибка.

### Раскладка

```
Заказы                                              42 всего
┌───────────────────────────────────────────────────────────┐
│  Все   ·   B2B   ·   Розница                              │  сегмент
├───────────────────────────────────────────────────────────┤
│ Все 42 │ Новые 3 │ Подтв. 7 │ Доставка 2 │ Заверш. 28 │ … │  статусы + счётчики
├───────────────────────────────────────────────────────────┤
│ 🔍 поиск по ID, номеру или телефону                       │
├───────────────────────────────────────────────────────────┤
│ #ID │ Клиент │ Сегмент │ Сумма │ Статус │ Дата │ ⋯        │
└───────────────────────────────────────────────────────────┘
```

Колонка «Тип» заменяется на «Сегмент» с бейджем B2B / Розница. Колонка «Статус»
остаётся: на вкладке «Все» она несёт информацию, на вкладке конкретного статуса
она избыточна, но убирать её на части вкладок — значит менять ширины колонок при
переключении, что хуже.

Счётчик со значением 0 показывается как есть, вкладка не прячется: исчезающие
вкладки ломают мышечную память.

### Действия из строки

Меню «⋯» в конце строки показывает только допустимые переходы плюс «Открыть».

Матрица переходов:

| Из | Куда можно |
|---|---|
| `pending` | `confirmed`, `cancelled` |
| `confirmed` | `in_delivery`, `cancelled` |
| `in_delivery` | `completed`, `cancelled` |
| `completed` | — (терминальный) |
| `cancelled` | — (терминальный) |
| `synced`, `failed` (легаси) | `confirmed`, `in_delivery`, `completed`, `cancelled` |

Из легаси-статусов выход открыт во весь рабочий поток — это спасательный люк для
исторических заказов. Входа обратно в `synced` / `failed` нет ни из одного
статуса: присваивать их больше нельзя.

`cancelled` терминален жёстко: отмена вернула товар на склад через
`OrderCancellationService`, а обратной операции (повторное списание при
восстановлении заказа) в системе нет. Разрешить выход из `cancelled` значило бы
создать заказ без списанного под него товара.

Отмена из списка идёт через диалог подтверждения — она не просто пишет статус, а
двигает склад. Остальные переходы выполняются одним кликом с оптимистичным
обновлением строки и откатом при ошибке.

### Валидация перехода на API

`OrderController::update` сейчас проверяет только принадлежность к
`Order::CLIENT_STATUSES`. Добавляется проверка допустимости перехода по матрице
выше; недопустимый переход → `422` с сообщением в формате валидации Laravel.

Матрица живёт на модели: `Order::ALLOWED_TRANSITIONS` (карта «из» → список
«куда») и метод `Order::canTransitionTo(string $status): bool`. Фронтенд держит
свою копию в `orderStatus.ts` — дублирование сознательное: фронт рисует меню, бэк
защищает данные, и оба должны работать, если второй недоступен.

**Известное следствие:** это строже, чем сегодня. Откат завершённого заказа в
«новый», который сейчас проходит, начнёт возвращать 422. Аварийный люк остаётся:
в Filament поле статуса — свободный `TextInput`
(`app/Filament/Resources/Orders/Schemas/OrderForm.php:34`), админ может
выставить там что угодно.

**Отдельно отмечено, вне объёма задачи:** запись статуса `cancelled` через
Filament проходит мимо `OrderCancellationService`, то есть товар на склад не
возвращается. Это существующий дефект, он не создаётся этой задачей и здесь не
чинится — но зафиксирован, чтобы не потеряться.

### Разбор страницы на компоненты

| Файл | Назначение |
|---|---|
| `admin/src/app/orders/page.tsx` | Тонкая обёртка: читает `searchParams`, держит запрос к API, раздаёт данные вниз |
| `admin/src/components/orders/OrderTabs.tsx` | Два ряда вкладок (сегмент, статус) со счётчиками |
| `admin/src/components/orders/OrdersTable.tsx` | Таблица, состояния загрузки и пустого списка, пагинация |
| `admin/src/components/orders/OrderRowActions.tsx` | Меню «⋯», диалог подтверждения отмены, вызов PATCH |
| `admin/src/components/orders/orderStatus.ts` | Единственный источник лейблов, цветов и матрицы переходов |

`orderStatus.ts` подключается и к карточке заказа
(`admin/src/app/orders/[id]/page.tsx`), где сейчас лежит вторая копия
`STATUS_STYLES` / `STATUS_LABELS`; копия удаляется. Выпадашка смены статуса в
карточке начинает предлагать только допустимые переходы — из того же источника.

Каталог `admin/src/components/orders/` новый; он повторяет уже принятую в проекте
раскладку `admin/src/components/{products,banners,collections,warehouse}`.

## Тестирование

### API (PHPUnit)

Новый файл `tests/Feature/Admin/AdminOrdersListTest.php`:

1. `filter[segment]=b2b` возвращает только заказы пользователей с `type = b2b`.
2. `filter[segment]=retail` включает заказ гостя (`is_guest = true`).
3. Без `filter[segment]` возвращаются заказы обоих сегментов.
4. `meta.status_counts` содержит все семь ключей; `archived` = сумма `synced` и
   `failed`.
5. `meta.status_counts` **не** меняется при переданном `filter[status]`.
6. `meta.status_counts` **меняется** при переданном `filter[search]`.
7. `meta.status_counts` учитывает `filter[segment]`.
8. `filter[status]=archived` возвращает заказы со статусами `synced` и `failed`
   и не возвращает рабочие.

Дополнения к `tests/Feature/Admin/OrderStatusAdminTest.php`:

9. Допустимый переход `pending → confirmed` возвращает 200 и пишет статус.
10. Недопустимый переход `completed → pending` возвращает 422 и статус не меняется.
11. Переход `pending → cancelled` проходит через `OrderCancellationService`
    (товар возвращается на склад) — проверяется через `stock_movements`.
12. Попытка присвоить `synced` возвращает 422.

Прогон: `php artisan test --compact --filter=AdminOrdersList` и
`--filter=OrderStatusAdmin`.
