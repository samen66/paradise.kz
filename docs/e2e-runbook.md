# Браузерная приёмка — как прогонять

> Дополнение к `docs/acceptance-checklist.md`. Чеклист ходит руками по трём
> фронтам; `php artisan mvp:acceptance` заменяет его на уровне API и базы.
> Остаётся третья часть — доказать, что нужное состояние **видно на экране**.
> Ей и занимаются Playwright-тесты в `storefront/`, `b2b-portal/` и `admin/`.

## Разделение труда

| Кто | Что доказывает |
|---|---|
| `php artisan mvp:acceptance` | остатки, суммы, статусы, движения склада, права, валидация — в базе и в API |
| Playwright | что это же состояние человек видит на экране: остатки, бейджи, плашки, цены, доступность кнопок, путь заказа |

Браузер не лезет в базу: остаток в базе и в API доказывает прогон. Зато число
**на экране** браузер сверяет — и это не дублирование: база и API могут быть
правы, а витрина показывать старое из кэша (см. «Что сейчас красное»). Эталон
для экрана — фикстуры (товар «в наличии» никто не покупает, его остаток всегда
ровно 7) или, для товара, который тесты покупают, публичный API в момент
проверки.

## Порядок обязателен: сначала artisan, потом Playwright

```bash
# 1. Состояние. Пересоздаёт базу, проходит пять сценариев приёмки, заводит
#    товары под браузер и выкладывает то, что после себя оставил, в
#    storage/app/private/acceptance-fixtures.json
php artisan mvp:acceptance --fresh --fixtures
#    в докер-стеке (без --no-interaction спросит подтверждение и откажется):
docker exec paradisekz-app-1 php artisan mvp:acceptance --fresh --fixtures --no-interaction

# 2. Экран — сьюты по очереди, не одновременно (см. «Повторный запуск»)
cd storefront  && npx playwright test
cd b2b-portal  && npx playwright test
cd admin       && npx playwright test

# 3. Снимки экрана каждого теста и шагов оформления заказа
npx playwright show-report
```

Под `--fixtures` прогон делает на два шага больше (раздел «ДЛЯ БРАУЗЕРНЫХ
ТЕСТОВ»): кроме распроданного товара прогона заводит

| Ключ в фикстурах | Остаток | Кто его трогает |
|---|---|---|
| `product` | 0 — выкуплен | никто: образец «Нет в наличии» |
| `in_stock_product` | 7 | никто: на экране всегда ровно 7 |
| `checkout_product` | 500 | тесты оформления заказа его покупают |

Фикстуры версии 1 (без этих товаров) тесты не принимают и просят повторить шаг 1.

Отдельного сидера у тестов нет и не нужно: данные делает прогон. Но все его
идентификаторы случайные (артикул, slug, телефоны, пароли) — иначе два прогона
подряд дрались бы за уникальные колонки. Мост между прогоном и тестами —
файл фикстур; тесты читают его через `e2e/fixtures.ts`.

Без прогона тесты падают сразу и по делу:

```
Нет фикстур приёмки: …/storage/app/private/acceptance-fixtures.json
Браузерные тесты идут поверх состояния, которое оставляет прогон приёмки. Сначала:
  php artisan mvp:acceptance --fresh --fixtures
```

### Что нужно поднять

| Что | Как |
|---|---|
| API на `:8000` | `composer run dev` или docker-стек |
| Дев-серверы фронтов | поднимать руками не нужно: `webServer` в конфиге поднимет сам (`reuseExistingServer` — если уже запущен, возьмёт его) |
| Браузер Playwright | один раз: `npx playwright install chromium` |

Порты: storefront `:3000`, b2b-portal `:3001`, admin `:3002` — как в
`CLAUDE.md`. Свой адрес можно подсунуть через `E2E_BASE_URL`, свои фикстуры —
через `ACCEPTANCE_FIXTURES`.

**Если красное всё и сразу — сначала среда.** Два случая, которые уже
встречались:

- база пересоздана после прогона (например, `migrate:fresh` руками) — в
  фикстурах товары, которых больше нет. Лечится шагом 1;
- дев-сервер Turbopack завис и отдаёт 404 на всех вложенных динамических
  маршрутах (`/product/{slug}`, `/catalog/{slug}`), даже не обращаясь к API,
  при том что `/catalog` и `/cart` открываются. Лечится перезапуском `npm run dev`.

## Что покрыто

### storefront (`:3000`)

`e2e/smoke.spec.ts`:

- главная открывается, несуществующий адрес отдаёт 404;
- каталог открывается и находит товар прогона по артикулу;
- карточка товара открывается из каталога;
- распроданный товар помечен «Нет в наличии», в карточке каталога нет кнопки
  «В корзину», а на странице товара кнопка заказа неактивна (мобильная панель)
  и отсутствует на десктопе.

`e2e/stock.spec.ts` — остатки:

- в одной выдаче каталога рядом «В наличии: 7 шт.» и «Нет в наличии»;
- «Только в наличии» убирает распроданный и оставляет товар в наличии;
- страница товара: «В наличии — 7 шт» и активная «В корзину» — на десктопе и
  в нижней панели на телефоне;
- корзина: 8 шт при остатке 7 — «Недостаточно на складе» и «Оформить заказ»
  неактивна; вернули 7 — снова можно.

`e2e/checkout.spec.ts` — оформление (тесты файла идут по очереди):

- пока страница товара открыта, товар покупают через API — после обновления
  страница товара и каталог показывают остаток на 1 меньше (ждём до 20 с;
  кэш витрины живёт 120 с, так что таймаут их различает);
- гость: карточка → «В корзину» → корзина на 2 шт с суммой → оформление
  (самовывоз, наличные) → страница «Спасибо» с номером → «Отследить заказ»
  находит заказ «В обработке» с позицией и суммой → корзина пуста;
- товар раскупили, пока покупатель оформлял: запрос заказа уходит с
  количеством больше остатка (перехватом в браузере — сам товар не выкупается),
  на экране «Товара «…» недостаточно на складе», остаток не тронут.

`e2e/order-tracking.spec.ts`:

- завершённый гостевой заказ прогона находится по номеру и телефону, статус
  написан словами, а не ключом перевода.

### b2b-portal (`:3001`) — `e2e/login.spec.ts`, `e2e/catalog.spec.ts`, `e2e/checkout.spec.ts`

- гостя не пускают в каталог и уводят на `/login`;
- неверный пароль объясняют по-русски;
- одобренный оптовик входит (`e2e/auth.setup.ts`, сессия — в `e2e/.auth/`);
- в каталоге у товара **оптовая** цена, розничной на экране нет;
- товар в наличии: «В наличии: 7 шт.» и кнопка «В корзину»;
- распроданный товар помечен и здесь;
- заказ целиком: «Быстрый заказ» по артикулу на 2 шт → корзина по оптовой
  цене → оформление → «Спасибо» с номером → заказ в «Мои заказы» «В обработке» →
  в каталоге остаток на 2 меньше;
- «Быстрый заказ» на 8 шт при остатке 7 в корзину не кладёт.

### admin (`:3002`) — `e2e/products.spec.ts`, `e2e/stock.spec.ts`, `e2e/orders.spec.ts`

- в списке товаров у распроданного товара бейдж «Нет остатка» (и код
  `out_of_stock` на экран не попадает);
- на «Складе» у товара в наличии тот же остаток 7, что видит покупатель;
- фильтр «Только проблемные» распроданность поломкой не считает;
- на «Складе» видно остаток по складу;
- при `meta.has_active_store: false` «Склад» показывает красную плашку «Нет ни
  одного активного склада» (ответ API подменяется на лету: выключить склад
  тестом нечем, склады живут в Filament);
- заказ проводится по рабочим статусам, и в выпадающем списке нет
  `synced`/`failed`.

## Повторный запуск

Данные меняют три места, и все переживают повтор:

- **админка** двигает статус заказа на выкуп остатка по кругу
  `Новый → Подтверждён → В доставке → Завершён` от того статуса, в котором его
  застала. «Отменён» не трогает намеренно: отмена вернула бы товар на склад и
  развалила бы проверки распроданного товара;
- **витрина** за прогон сьюта покупает 3 шт товара «для заказа» (1 — «чужой»
  заказ через API, 2 — гость через экран);
- **портал** покупает 2 шт того же товара.

500 шт хватает примерно на сотню прогонов. Поэтому тесты оформления сверяют
остаток не с фикстурами, а «до/после»: до — из API или с экрана, после — на
столько меньше. Отсюда и правило **сьюты витрины и портала — по очереди**:
запущенные одновременно, они купят товар друг у друга между «до» и «после».

Хочется чистого листа — повторите шаг 1.

## Что сейчас красное и почему (2026-09-16)

Четыре теста падают не из-за тестов, а из-за приложения. Каждый падает с
сообщением, которое называет причину.

| Тест | Что видно | Где причина |
|---|---|---|
| storefront `checkout.spec.ts` › «после покупки витрина сразу показывает уменьшенный остаток» | API уже отдаёт 499, а страница товара или каталог (бывает, что одна из двух, бывает — обе) ещё до двух минут показывают 500 | Страницы кэшируются (`revalidate: 120`), а сброс кэша висит на `ProductObserver`. `FifoInventoryService` пишет `products.stock` через query builder, observer не срабатывает — после заказа, отмены и приёмки кэш не сбрасывается. Локально вдобавок `RevalidateStorefrontCacheJob` падает: из контейнера `STOREFRONT_URL=http://localhost:3000` не достаёт до хоста |
| storefront `checkout.spec.ts` › «гость оформляет заказ…» | заказ создан, но покупателя уносит на `/cart`, страницу «Спасибо» с номером он не видит | `storefront/src/app/[locale]/checkout/page.tsx`: `clear()` опустошает корзину, и эффект «корзина пуста → `router.replace("/cart")`» перебивает `router.push` на `/checkout/success` |
| storefront `order-tracking.spec.ts` | вместо статуса «account.status.completed» | в `messages/ru.json` (и `kk.json`) у `account.status` только `pending`/`synced`/`failed` — нет `confirmed`, `in_delivery`, `completed`, `cancelled` |
| b2b-portal `checkout.spec.ts` › «партнёр оформляет заказ…» | на оформлении «Итого 0 ₸», кнопка неактивна — заказ не оформить | корзина и оформление портала ходят в `POST /api/cart/validate` и `POST /api/checkout`, таких маршрутов нет (у B2B — `POST /api/orders`). Корзина это прячет: при ошибке сверки считает сумму сама |

Когда причину починят, тест станет зелёным без правок.

## Чего в тестах нет намеренно

- **Карточки товара в b2b-portal.** `/product/{slug}` там сейчас не
  открывается: страница просит у API `/api/products/{slug}`, а этот маршрут
  принимает только id и отдаёт 404. Пока не починено в приложении — теста нет:
  вечно красный тест хуже отсутствующего.
- **Старые B2B-спеки из storefront.** Они ходили по `/b2b/*`, которых в
  storefront больше нет; переехало не «как было», а то, что имеет смысл —
  вход, гейт портала и оптовая цена.
