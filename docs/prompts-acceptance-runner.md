## Что автоматизируется, а что нет — прочти перед запуском

Чеклист проверяет две разные вещи, и они требуют разных инструментов:

| Что | Чем автоматизируется |
|---|---|
| Бизнес-цепочка: товар → приёмка → остаток → заказ → статусы → отмена → возврат остатка, плюс целостность данных | **Промпт 1** — artisan-команда. Детерминированно, быстро, годится в CI |
| Рендер интерфейса: видит ли менеджер бейдж, неактивна ли кнопка, показана ли оптовая цена | **Промпт 2** — Playwright. Медленнее, флакует, но только он доказывает, что человек это увидит |

Промпт 1 закрывает ~80% чеклиста и даёт максимум пользы на единицу усилий. Делай его первым.
После него ручным останется только то, что надо глазами посмотреть.

## Промпт 1 — artisan-команда `mvp:acceptance`

```
Прочитай docs/acceptance-checklist.md — там пять сценариев приёмки MVP, которые сейчас
проходят руками. Нужно свести их в одну artisan-команду, которая прогоняет всю цепочку
и печатает отчёт.

СОЗДАТЬ: app/Console/Commands/MvpAcceptanceCommand.php, сигнатура `mvp:acceptance`.

Как команда должна ходить в приложение:

НЕ дёргай сервисы напрямую там, где чеклист ходит через HTTP — иначе проверка докажет
меньше, чем ручной прогон. Прогоняй запросы через полный стек роутинга и middleware,
не поднимая веб-сервер:

    $response = app()->handle(Request::create($uri, $method, [], [], [], $server, $content));

с заголовками Accept: application/json и Authorization: Bearer <token> где нужно.
Токены получай через $user->createToken('acceptance')->plainTextToken.
Добавь опцию --url=, которая вместо этого бьёт по реальному HTTP (Http::) — пригодится,
чтобы проверить уже задеплоенный стенд.

Что проверять, по шагам чеклиста (каждый шаг — отдельная строка отчёта с ✓/✗):

  ПОДГОТОВКА
  1. Есть активный склад; есть роли admin/manager/b2b_customer; есть типы цен retail и b2b.

  СЦЕНАРИЙ 1 — товар доезжает до витрины
  2. POST /api/admin/products (админским токеном) создаёт товар с названием, категорией,
     розничной и оптовой ценой.
  3. У созданного товара непустой slug — его ставит Product::booted(), проверь что реально встал.
  4. GET /api/admin/products показывает его с issues, содержащим no_stock.
  5. Проведи приёмку на 10 шт через GoodsReceiptService (это единственный легальный способ
     завести остаток — напрямую в products.stock писать нельзя).
  6. products.stock == 10 И product_store_stock.stock == 10.
  7. GET /api/public/products отдаёт товар с in_stock: true.
  8. GET /api/public/products/{slug} открывается (200), не 404.

  СЦЕНАРИЙ 2 — B2C-заказ
  9. POST /api/public/checkout на 3 шт → 201, номер формата P-XXXXXX.
  10. Статус заказа ровно `pending`. Если `failed` — это регресс, который мы уже чинили:
      где-то вернулся push в ERP. Отчёт должен назвать это прямым текстом.
  11. Остаток стал 7 и 7 (агрегат и склад).
  12. Задиспатчено уведомление менеджеру о новом заказе. Очередь тут database, так что
      проверяй появление строки в таблице jobs (или перехвати через Bus::fake, если
      получится сделать это чисто внутри команды — на твоё усмотрение, главное чтобы
      проверка была настоящей, а не всегда-зелёной).
  13. PUT /api/admin/orders/{id} проводит статус по цепочке confirmed → in_delivery → completed.
  14. PUT с status=synced или failed → 422 (легаси-статусы назначать нельзя).
  15. GET /api/public/orders/track?number=&phone= находит заказ.

  СЦЕНАРИЙ 3 — B2B
  16. POST /api/auth/register заводит B2B-клиента.
  17. Неодобренный клиент получает 403 на GET /api/products.
  18. app(ApproveClient::class)->handle($user) отрабатывает БЕЗ исключения.
      Раньше тут падало «Внешняя учётная система не подключена» — это регресс, назови его явно.
  19. POST /api/auth/login по телефону выдаёт токен.
  20. GET /api/products отдаёт оптовую цену (b2b_price), а не розничную.
  21. POST /api/orders на 2 шт → 201, остаток стал 5.

  СЦЕНАРИЙ 4 — отмена возвращает остаток
  22. PUT /api/admin/orders/{id} со status=cancelled → остаток вернулся на 7 и 7.
  23. В stock_movements по этому заказу есть строка type=return, и её unit_cost РАВЕН
      unit_cost приёмки (себестоимость), а не цене продажи. Это отдельная проверка —
      если сюда попадёт цена продажи, поедет маржа, и молча.
  24. Повторная отмена → 422, остаток не вырос второй раз.
  25. Отмена через кабинет клиента: PATCH /api/account/orders/{id}/cancel на новом
      pending-заказе тоже возвращает остаток.

  СЦЕНАРИЙ 5 — распроданный товар
  26. Выкупи весь остаток. GET /api/public/products → in_stock: false.
  27. filter[in_stock]=1 не возвращает этот товар.
  28. POST /api/public/checkout на него → 422 с сообщением на русском.
  29. Остаток нигде не ушёл в минус.

  ЦЕЛОСТНОСТЬ (три запроса из раздела 6 чеклиста)
  30. Для каждого товара products.stock == сумме product_store_stock по складам.
  31. Нет ни одной строки product_store_stock со stock < 0.
  32. Нет заказов в статусах synced/failed.
  33. php artisan stock:recompute ничего не меняет (агрегаты уже верны) — сравни
      снимок products.stock до и после.

БЕЗОПАСНОСТЬ — это важнее самой команды:

  Команда создаёт и меняет РЕАЛЬНЫЕ данные в текущей базе. Запуск по ошибке на проде
  недопустим. Поэтому:
  - если app()->environment() не local/testing — отказывайся работать и объясняй почему;
    обойти можно только явным --force;
  - опция --fresh сама делает migrate:fresh --seed перед прогоном (с подтверждением,
    если не передан --no-interaction). Это рекомендуемый способ запуска — так прогон
    начинается с чистого листа и повторяем;
  - без --fresh команда работает поверх текущих данных и ЧЕСТНО предупреждает в отчёте,
    что оставила после себя тестовые строки (товар, заказы, движения по складу);
  - все создаваемые сущности помечай узнаваемо (например, артикул с префиксом ACC-
    и e-mail/телефон из заведомо тестового диапазона), чтобы их потом можно было найти.

ВЫВОД:

  Таблица шагов с ✓/✗, под ней итог вида «33 шага: 31 пройден, 2 провалено».
  Для каждого проваленного шага — что ожидали, что получили, и (если это один из
  известных регрессов — шаги 10, 18, 23) прямое указание, какая именно поломка вернулась.
  Код возврата: 0 если всё зелёное, 1 если хоть один шаг красный.
  Опция --stop-on-failure, чтобы останавливаться на первом провале.

ТЕСТ НА САМУ КОМАНДУ:

  tests/Feature/Acceptance/MvpAcceptanceCommandTest.php — прогоняет команду на sqlite
  (RefreshDatabase) и проверяет, что она завершается успешно. Это защищает от того, что
  команда сгниёт незаметно вместе с кодом, который проверяет.
  Отдельным кейсом: на production-окружении без --force команда отказывается работать.

ПРАВИЛА ПРОЕКТА, которые нельзя нарушить:
  - в products.stock и product_store_stock пишет только FifoInventoryService;
  - МойСклад удалён, возвращать нельзя;
  - php artisan test --compact должен остаться зелёным.

Проверка перед сдачей:
  php artisan test --compact
  php artisan mvp:acceptance --fresh --no-interaction
  vendor/bin/pint --dirty
```

## Промпт 2 — привести Playwright в порядок и закрыть UI

```
В storefront/e2e уже есть набор Playwright-тестов, но он устарел: B2B-витрина переехала
из storefront в отдельное приложение b2b-portal на порт 3001, а спеки
e2e/checkout/b2b-checkout.spec.ts, e2e/auth/b2b-email.spec.ts и e2e/tests/b2b-flow.spec.ts
до сих пор ходят по маршрутам /b2b/*, которых в storefront больше нет.

Задача — разобраться с этим и закрыть ту часть приёмки (docs/acceptance-checklist.md),
которую artisan-команда mvp:acceptance доказать не может: что человек реально видит
нужное состояние на экране.

1. Разберись, какие из существующих спеков ещё осмысленны, какие починить, какие удалить.
   Не оставляй тесты, которые ходят по несуществующим маршрутам, — пусть лучше их не будет,
   чем они будут вечно красными и все привыкнут их игнорировать.

2. B2B-спеки переезжают в b2b-portal вместе с витриной: заведи там playwright.config.ts
   по образцу storefront (baseURL localhost:3001) и перенеси то, что переносимо.

3. Админка (admin/, порт 3002) сейчас без e2e вообще. Заведи минимум:
   - список товаров показывает бейдж причины, по которой товар не на витрине;
   - страница «Склад» показывает остаток, а при отсутствии активного склада — красную плашку;
   - заказ можно провести по статусам, и в выпадающем списке нет synced/failed.

4. На storefront оставь и почини smoke-набор: каталог открывается, карточка товара
   открывается, распроданный товар показан как «нет в наличии» и кнопка неактивна.

Важно про данные: Playwright-тестам нужно предсказуемое состояние базы. Не выдумывай
отдельный сидер — используй `php artisan mvp:acceptance --fresh`, она как раз оставляет
после себя товар с известным остатком и заказы в разных статусах. Опиши в README прогона,
что сначала запускается она, потом Playwright.

Не пытайся покрыть браузером то, что уже покрыто artisan-командой: остатки, суммы,
статусы в базе проверяются там, быстрее и надёжнее. Браузер нужен только чтобы доказать,
что это видно на экране.

Проверка:
  cd storefront && npx tsc --noEmit && npx playwright test
  cd b2b-portal && npx tsc --noEmit && npx playwright test
  cd admin && npx tsc --noEmit && npx playwright test
```

## Промпт 3 — поставить приёмку в CI (после первых двух)

```
Добавь в .github/workflows/ci.yml job `acceptance`, который поднимает mysql как сервис,
ставит зависимости, накатывает миграции и сидеры и прогоняет `php artisan mvp:acceptance
--fresh --no-interaction`.

Смысл: юнит- и feature-тесты гоняются на sqlite in-memory, а приёмка должна пройти на
MySQL — ровно там уже ловились расхождения (например, поведение NOT NULL и типов decimal).

Playwright в CI пока не добавляй: он требует поднятого API и трёх фронтов, это отдельная
история, и на первых порах он будет флакует больше, чем ловить. Заведи отдельным шагом
только когда набор из промпта 2 отстоится локально.
```
