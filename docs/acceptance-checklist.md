# Приёмка MVP — пошаговый прогон

> Пять сценариев из `docs/mvp-plan-2026-09.md` (раздел 9), расписанные под локальную среду.
> Идти сверху вниз. На каждом шаге написано, что должно получиться — если получилось
> другое, останавливайся и скажи мне номер шага и что увидел.
>
> Автотесты покрывают код. Этот прогон проверяет то, чего они не видят: что менеджер
> реально может завести товар, а покупатель — его купить.

---

## 0. Поднять среду

```bash
# 1. Чистая база: роли, типы цен, склад по умолчанию, админ
php artisan migrate:fresh --seed

# 2. API + очередь + логи (в одном терминале)
composer run dev            # artisan serve :8000, queue:listen, pail, vite

# 3. Фронты — каждый в своём терминале
cd storefront  && npm run dev          # :3000
cd b2b-portal  && npm run dev          # :3001
cd admin       && npm run dev -- -p 3002
```

**Очередь обязана работать.** На ней висят уведомления и сброс кэша витрины
(`RevalidateStorefrontCacheJob`). Без неё товар может не появиться на storefront сразу —
и ты решишь, что сломан каталог, хотя сломан кэш.

**Перед стартом проверь `.env`:**

| Переменная | Значение для прогона | Зачем |
|---|---|---|
| `SMS_DRIVER` | `log` | Код для входа B2C попадёт в лог, а не в реальную SMS |
| `BROADCAST_CONNECTION` | `log` | Иначе сохранение товара уйдёт вещать в Reverb; если он не поднят — job упадёт |
| `STOREFRONT_URL` | `http://localhost:3000` | Куда слать сброс кэша |
| `QUEUE_CONNECTION` | `database` | Как в проде |

Доступы и адреса:

| Что | Где | Вход |
|---|---|---|
| Бэк-офис (Filament) | http://localhost:8000/admin | `admin@paradise.kz` / `password` |
| Админка (SPA) | http://localhost:3002 | те же |
| Витрина B2C | http://localhost:3000 | — |
| Портал B2B | http://localhost:3001 | заведём в сценарии 3 |

- [ ] Всё поднялось, админка и обе витрины открываются

## 2. B2C-заказ принимается и обрабатывается

- [ ] **2.1** Витрина → карточка товара → «В корзину» (**3 шт**) → Корзина.
      Суммы считаются, товар доступен.

- [ ] **2.2** Оформление: имя, телефон, **самовывоз**, оплата при получении. Оформить.
      → Страница успеха, номер заказа вида **`P-100001`**.

- [ ] **2.3** Вернись на витрину: у товара остаток **7** (или просто «в наличии»).

      Проверка в базе — оба числа должны совпадать:
      ```sql
      SELECT p.id, p.stock AS aggregate, pss.stock AS at_store
      FROM products p JOIN product_store_stock pss ON pss.product_id = p.id;
      ```
      → **7.000 и 7.000.** Если агрегат отстал — это тот самый баг, который чинили; скажи мне.

- [ ] **2.4** Админка → **Заказы**. Заказ в статусе **«Новый»**.
      → **Не «Ошибка».** Если «Ошибка» — значит где-то остался push в ERP, скажи мне.

- [ ] **2.5** Открой заказ: позиции, суммы, контакты, способ доставки — всё на месте.

- [ ] **2.6** Смени статус: «Подтверждён» → «В доставке» → «Завершён».
      В выпадающем списке **нет** статусов «Синхронизирован» и «Ошибка» —
      только пять рабочих.

- [ ] **2.7** WhatsApp пока не настроен, так что вместо сообщений смотри лог:

      grep -i whatsapp storage/logs/laravel.log | tail -5

      плюс одна на создание заказа (уведомление менеджеру). Это ожидаемо.
      Если строк нет вообще — уведомления не диспатчатся, скажи мне.

- [ ] **2.8** Витрина → «Отследить заказ» → номер `P-100001` + тот же телефон.

## 4. Отмена возвращает остаток

- [ ] **4.1** Админка → Заказы → B2B-заказ из шага 3.6 → статус **«Отменён»**.

- [ ] **4.2** Остаток вернулся с 5 на **7**. Проверь тем же SQL из шага 2.3 —
      агрегат и складской остаток снова совпадают.

- [ ] **4.3** Возврат записан в журнал по себестоимости, а не по цене продажи:
      ```sql
      SELECT type, qty_delta, unit_cost FROM stock_movements
      WHERE product_id = <id> ORDER BY id;
      ```
      → Строки: `receipt +10`, `sale -3`, `sale -2`, `return +2`.
      У `return` **та же `unit_cost`, что у `receipt`** (себестоимость приёмки),
      а не цена, по которой продали.

- [ ] **4.4** Попробуй отменить тот же заказ ещё раз.
      → Не даёт. Остаток не вырос второй раз.

- [ ] **4.5** Клиентская отмена: с витрины B2C оформи ещё один заказ и отмени его
      в личном кабинете, пока он «Новый».
      → Остаток вернулся. Заказ в статусе «Подтверждён» отменить уже нельзя.

## 6. Финальная проверка целостности

```sql
-- Остатки нигде не разошлись: строк быть не должно
SELECT p.id, p.name, p.stock AS aggregate, COALESCE(SUM(pss.stock),0) AS sum_by_store
FROM products p LEFT JOIN product_store_stock pss ON pss.product_id = p.id
GROUP BY p.id, p.name, p.stock
HAVING p.stock <> COALESCE(SUM(pss.stock),0);

-- Ни одного отрицательного остатка
SELECT * FROM product_store_stock WHERE stock < 0;

-- Ни одного заказа в мёртвых статусах
SELECT id, number, status FROM orders WHERE status IN ('synced','failed');
```

- [ ] Все три запроса вернули пусто
- [ ] `php artisan test --compact` — зелёный
- [ ] `php artisan stock:recompute` отработал и **ничего не изменил** (агрегаты уже верны)

## Автоматом вместо рук

Этот прогон целиком повторяет `php artisan mvp:acceptance --fresh` — те же пять
сценариев, только запросами через полный HTTP-стек, без веб-сервера. Она
проверяет базу и API; то, что нужное состояние **видно на экране**, доказывают
браузерные тесты в `storefront/`, `b2b-portal/` и `admin/`. Порядок и команды —
в `docs/e2e-runbook.md`:

```bash
php artisan mvp:acceptance --fresh --fixtures
cd storefront && npx playwright test   # то же для b2b-portal и admin
```

Руками этот чеклист остаётся нужен там, где ни то, ни другое не достаёт: фото
товара, WhatsApp-сообщения, вид писем, реальный Filament.
