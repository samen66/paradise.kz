# AGENTS.md — Furniture Shop MVP

Этот файл — основной контекст проекта для AI-агента в Cursor. Он загружается автоматически и должен оставаться в корне репозитория (это аналог `CLAUDE.md` для Claude Code).

## О проекте

Интернет-магазин мебели для компании с офлайн-магазином в Алматы и поставками из Китая. Заменяет текущий процесс (заказы вручную через WhatsApp/Instagram) на автоматизированную платформу.

**Два сегмента клиентов:**
- **B2C** — частные покупатели, розничные цены, простой каталог и заказ
- **B2B** — магазины-партнёры (оптовые покупатели) из разных городов Казахстана, отдельные цены, нужен быстрый заказ по списку товаров и просмотр остатков в реальном времени

**Текущая инфраструктура:**
- Учёт товаров, цен и остатков ведётся в самом приложении: каталог — в админке, остатки — в локальном FIFO-журнале. Внешней ERP нет (интеграция с МойСклад удалена)
- Два физических объекта: склад + showroom в Алматы
- Своя курьерская служба + самовывоз

**Бизнес-цель MVP:** автоматизировать то, что сейчас делается вручную — узнать наличие товара, посмотреть фото, оформить заказ/бронь — без необходимости писать в WhatsApp.

## Стратегия и приоритеты

MVP должен быть запущен за 1–2 месяца. Из-за этого:
- **Не реализуем** в MVP: AI-подбор мебели под интерьер, AI-поиск по фото, AI-чат-консультант, полноценный мультивендорный маркетплейс — это Этап 2/3, см. `docs/roadmap.md` (если создан)
- **Реализуем в MVP**: каталог, локальный складской учёт (FIFO), личный кабинет B2C/B2B, заказ, бронирование, базовая админка
- При выборе между "сделать быстро и просто" и "сделать гибко на будущее" — для MVP **выбираем быстро и просто**, но не создаём технический долг, который трудно будет переделать (например: структура БД должна закладывать будущие поля, даже если функционал пока не реализован)

## Технологический стек

| Слой | Технология |
|---|---|
| Backend | Laravel 13 (PHP 8.4 в прод-образе), API-only (без Blade-шаблонов для публичной части) |
| Frontend | Три Next.js-приложения (App Router, TypeScript) + zustand: `storefront/` (B2C, next-intl ru/kk), `b2b-portal/` (B2B), `admin/` (операционная админка менеджера) |
| Стейт-менеджмент | zustand (раздельные сторы для B2C и B2B) |
| Стили | Tailwind CSS |
| Auth | Laravel Sanctum (токены, не sessions — фронт отдельный) |
| Роли | spatie/laravel-permission |
| Админка | `admin/` (Next.js) — заказы, товары, клиенты; Filament (`/admin` на API-хосте) — приёмки, склады, типы цен, CMS |
| Очереди | Laravel Queue + Redis |
| База данных | MySQL |

**Почему так:** Backend и frontend разделены, потому что в будущем планируется B2B-приложение на Flutter — оно будет использовать ту же Laravel API, что и веб-версия. Не привязываемся к Inertia/Blade, чтобы не закрывать этот путь.

## Ключевые сущности данных

- `users` — клиенты и сотрудники (роли: admin, manager, b2b_customer; у B2C-покупателя роли нет), для B2B есть company_name, company_bin, is_approved
- `products` — товары, есть цены по типам цен и legacy-колонки `retail_price` / `b2b_price`; `products.stock` — агрегат остатка по всем складам
- `stock_movements` — append-only журнал движений (источник правды по остаткам), `batches` — FIFO-партии с себестоимостью, `product_store_stock` — проекция остатка по складам
- `orders` / `order_items` — заказы, type различает обычный заказ (online_order) и бронь (reservation)

Полная схема — см. `docs/database-schema.md`.

## Правила для агента при работе с кодом

1. **Источник правды по остаткам — локальный FIFO-журнал (`stock_movements`). Ни один код не пишет в `products.stock` и `product_store_stock` напрямую — только через `FifoInventoryService`.** Остатки меняются только проведением приёмки, заказом и его отменой; ручного редактирования остатка нет ни в одной админке.
2. **Не дублируй бизнес-логику склада.** Приход, списание и возврат — методы `FifoInventoryService` (`receive()`, `issue()`); текущий остаток — `onHand()` или проекция `product_store_stock`. Не считай остатки своими SQL-запросами к `stock_movements` / `batches`.
3. **Различай B2C и B2B логику явно**, не смешивай в одном контроллере без необходимости — разные цены, разные права, разные сценарии (бронирование важно для B2B).
4. **Перед добавлением нового npm/composer пакета** — проверь, не покрывается ли задача уже установленным пакетом из списка выше. Не предлагай новые зависимости без явной причины.
5. **Не зависимости "из головы".** Перед использованием метода Laravel/Vue/Filament/spatie-пакета, в котором ты не уверен — проверь актуальную сигнатуру в установленном пакете (`vendor/` для PHP, `node_modules/` для JS) или в официальной документации, а не предполагай по training data.
6. **Внешних ERP нет.** Не возвращай вызовы МойСклад. Новый источник импорта (если понадобится) подключается за контрактами `App\Contracts\Erp\ErpProvider` / `App\Contracts\Catalog\CatalogSource`; при интеграции используй реальную структуру ответа из документации API, не предполагай поля.
7. **Для МVP не строй мультивендорный маркетплейс** — даже если архитектура "напоминает" Kaspi/Ozon, в текущем релизе один продавец (наша компания).

## Стиль кода

- PHP: PSR-12, строгая типизация (`declare(strict_types=1)` в новых классах), early return вместо глубокой вложенности
- Vue: Composition API + `<script setup lang="ts">`, без Options API
- Коммиты: Conventional Commits (`feat:`, `fix:`, `refactor:`)
- Текст интерфейса — русский (целевая аудитория — Казахстан), но код, переменные, комментарии — на английском
